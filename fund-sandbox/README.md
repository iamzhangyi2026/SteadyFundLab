# fund-sandbox

**虚拟资金 + 真实规则的基金交易沙盒。**

用模拟资金验证基金交易策略，但所有交易规则完全对接真实世界：支付宝的费率标准、
T+1 份额确认、15:00 截单、7 天惩罚性赎回费、先进先出（FIFO）份额消耗、分红除息。
交易由 AI 主导执行，人负责总控与风控。

---

## 定位

| | 人工操作 | 本系统 |
|---|---|---|
| 资金 | 真实 | 虚拟 |
| 决策 | 人拍板 | 接管 agent 亲自下达（人工总控 + AI 执行） |
| 定位 | 实战 | 试验场 |
| 产出 | 人工下单 | 决策 + 分析结论 |

本系统用虚拟资金验证策略，产出的分析结论供人参考，**但不负责真实资金**。

> ### ⚠️ 资金性质声明
> **系统内所有资金（初始资金、月度配额、现金余额、持仓市值、盈亏）均为模拟数据，
> 仅用于演示 / 测试 / 策略验证，不具备任何真实货币价值，不代表真实账户或真实交易结果。**
> 除资金为模拟外，其余部分——交易规则（费率、截单、确认、结算、风控）、行情与净值等数据、
> 业务流程与界面交互——均按真实逻辑实现并以真实数据源驱动，不因资金为模拟而降真。

规则内核来自长期实战迭代：买卖纪律线、数据双源交叉验证、防假消息分级、披露态/落地态区分。
「不自动下单，等人拍板」这条在本项目被替换为「接管 agent 亲自决策执行 + 人工总控」（系统无自治交易，定投是唯一自动执行项）。

## 架构

```
数据抓取（akshare + RSS 自动拉取）
        ↓
  市场快照（统一格式）  ← 接口边界
        ↓
  情报自动采集（RSS 新闻 → 关键词初筛 → intel_events；规则只做初筛，定性修正仍由 AI）
        ↓
  决策层（只有 AI）
  接管 agent经 API 亲自决策
        ↓
  交易指令（统一格式）  ← 接口边界
        ↓
风控 → 交易引擎 → 记账
```

两条接口边界是关键：**上面是统一的市场快照，下面是统一的交易指令。**
决策一律由 AI 经 `POST /api/order` 下达，数据层、引擎、前端一行都不用动。
**系统不做任何自动决策**——没有规则兜底、没有内置模型代决策。

### AI 接管：离线时系统等待，没有兜底

| AI 状态 | 谁决策 | 系统行为 |
|---|---|---|
| 在线（心跳未超时） | AI | 按 AI 指令执行 + 风控拦截 |
| 离线（超 6 小时无心跳） | 无人 | 只在界面亮出「AI 离线」，不自动交易 |

**没有规则兜底**：AI 离线时规则引擎不会「升格」为决策者，系统就等着。
定投是唯一例外——金额与扣款日由纪律事先定好，仍按期自动扣款。

判定"在不在"靠心跳文件 `data/heartbeat.json`——AI 每次参与运作刷新时间戳，
超过 `heartbeat_timeout_hours` 判定离线（`backend/engine/coordinator.py`）。

规则引擎的纪律线（来自长期实战迭代的规则）：

| 条件 | 动作 |
|---|---|
| 浮盈 ≥ +20% | 兑现，减仓 50% |
| 从 60 日高点回撤 ≥ 15% | 减仓 50% |
| 亏损 ≥ 5% 且跑输基准 | 认错，清仓 |
| 每周定投日 | 按 25 元/只扣款 |
| 赎回前 | 检查是否踩 7 天惩罚费 |

## 基金筛选：不看名称，只看持仓

**风格漂移很常见**——名为「XX新兴成长」的可能重仓银行股，名为「XX消费」的可能满仓新能源。
所以分析必须穿透到实际持仓（`backend/engine/holdings.py`）：

- **行业暴露**：直接取行业配置接口，比「抓重仓股 → 反查行业」更直接
- **漂移检测**：名称宣称的方向 vs 实际持仓占比，差太多就标告警
- **重叠度**：两只基金前十大重仓股重叠 ≥3 只 = 假分散，买了等于没分散

**可投范围只限场外**（不需要股票账户）：ETF联接、LOF、QDII、混合型、股票型、指数型、债券型。
这里有个坑——「XX ETF 联接」是场外可定投，但「XX ETF」是场内需股票账户，
两者只差两个字，靠类型字段区分，**不能只看名称放行**。

## 资金规则

| 项 | 值 |
|---|---|
### 可用预算（累积制）

    可用预算 = 初始资金 + 历史累积新增 − 已用金额 + 投资收益
    投资收益 = 累计赎回金额 + 累计分红 − 累计申购金额（可为负）

| 项 | 值 |
|---|---|
| 初始资金 | 1000 元 |
| 每月新增 | 1000 元（**累积**，不清零） |
| 单只定投 | 25 元/周 = 100 元/月 |
| 用途 | 买入（一次性）+ 定投，**两者共享同一池子** |
| 买入金额 | **不固定**，完全由你决定，唯一硬约束是不超可用预算 |

两个关键点：

1. **累积制，不是每月清零**。每月新增 1000 是往池子里累加，
   不是「当月不用就作废」。第二个月可用 = 1000 + 2000 − 已用 + 收益。
2. **盈亏反过来影响可用预算**。赚到的钱可以继续投，亏掉的钱削减额度。

注意：只有**已实现**盈亏计入可用预算。持仓的浮动盈亏不计入——
账面上赚着但赎回来才发现要扣赎回费，计进去会让可用预算虚高。

会计等价校验（代码里 `budget.check_consistency()` 会验证）：

    可用预算 ≡ 现金余额 = 初始 + 累积新增 − 累计申购 + 累计赎回 + 累计分红

两个算法路径完全不同（一个从持仓批次算、一个从流水累加），
对不上就说明账目有问题，必须查清楚而不是将就用。

### 定投 vs 一次性买入：纪律性正好相反

| | 金额 | 谁决定 |
|---|---|---|
| **定投** | **固定** 25 元/周/只 | 分析只决定投哪些，不决定投多少。不因行情改变 |
| **一次性买入** | **完全由你决定** | 无固定档位，唯一硬约束是不超可用预算 |

定投的意义就是用固定节奏摊平成本、避免择时，所以金额不能被行情左右。
每周自动执行（幂等，同一自然周不会重复扣款），无论 AI 在线与否。**扣款周几在买入时自选**（默认周一，仅限周一至周五）。扣款规则对齐支付宝基金定投：定投日当天 **15:00 前**按当日净值成交；定投日**仅限周一至周五**，遇周末/法定节假日**自动顺延至下一交易日**，顺延与下一扣款日重合则仅扣一次。钟点固定（同支付宝），周几自选。

预算不足时定投是**跳过而不是缩水**——缩水成小额会破坏"固定节奏"这个核心。

### 风控（实测均生效）

| 规则 | 实测 |
|---|---|
| 无理由不下单（AI/规则源） | 空 reason 直接拒绝；人工操作选填（人即总控） |
| 单只持仓上限 25% | 小额账户一次买 300 元会被拒（买入后占比达 75%） |
| 单笔上限 / 单日次数 | 配置化，超限拒绝 |
| 待确认订单冻结 | 从可用预算扣除，防止连续下单导致 T+1 透支 |
| 账户回撤止损 20% | 峰值法，触发后**只告警不自动清仓** |

单只占比必须按**买入后**计算：这笔买入会同时抬高该基金市值和总市值，
用当前占比判断会漏掉"小额账户一次性重仓"。

回撤止损用峰值法（meta 表存历史最高），不建每日快照表——效果等价但复杂度低得多。
触发后暂停自动交易交给人或 AI 决定，**不自动割肉**（自动割往往割在低点）。

## 费率规则

**管理费与托管费绝不计算** —— 已按日从净值中计提，公布的净值就是扣除后的。
重复计算会让收益严重失真。只算交易成本：申购费 + 赎回费。

申购费采用**外扣法**：`净申购金额 = 申购金额 / (1 + 费率)`
费率 = 基金原始费率 × 渠道折扣（支付宝是部分基金 1.25 折起，**不是全部 1 折**，
所以必须逐只按实际费率算，不能写死 0.15%）。

赎回费阶梯（证监会规定，全渠道统一）：

| 持有天数 | 费率 |
|---|---|
| < 7 天 | 1.50% ← 惩罚性 |
| 7 ~ 30 天 | 0.75% |
| 30 天 ~ 1 年 | 0.50% |
| 1 ~ 2 年 | 0.25% |
| ≥ 2 年 | 0% |

持有天数按**自然日**算，不是交易日。

## HTTP 接口

启动（只监听本机回环地址）：

```bash
runtime\python\python.exe -m backend.api.main
# 或
runtime\python\python.exe -m uvicorn backend.api.main:app --host 127.0.0.1 --port 8765
```

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/order` | 下单。`reason`：外部 AI / 规则引擎必填（空理由拒绝）；人工操作选填 |
| GET | `/api/orders` | 订单列表，可 `?status=pending` 过滤 |
| GET | `/api/account` | 账户概览（现金、市值、配额、模式） |
| GET | `/api/positions` | 持仓明细，**罚期倒计时按批次给出** |
| GET | `/api/status` | 运行状态（混合模式 / AI 是否在线） |
| POST | `/api/heartbeat` | 刷新心跳，AI 每次操作应调用 |
| GET | `/api/health` | 六维健康（engine/health.py：净值/持仓/订单/资金/纪律/数据新鲜度） |
| GET | `/api/data-health` | 数据源健康度（失败可见，含 record_count/message/created_at） |
| POST | `/api/intel` | 情报入库（status 须区分 disclosed / landed） |
| GET | `/api/intel` | 情报库列表（自动采集 + 人工/AI 补录，含来源链接） |
| POST | `/api/intel/collect` | 手动触发情报自动采集，返回 `{"ok":true,"collected":N}` |
| GET | `/api/boards` | 板块资金流信号；`?limit=0` 返回全量 90 个（弹窗发散条形图用） |
| GET | `/api/market-news` | RSS 财经新闻（广义），`?day=YYYY-MM-DD&limit=N` 过滤 |
| GET | `/api/analysis` | 分析页聚合数据（行业暴露、收益曲线、资讯流等） |
| GET | `/api/exposure` | 持仓行业暴露（单基金 + 组合加权） |

下单示例：

```bash
curl -X POST http://127.0.0.1:8765/api/order \
  -H "Content-Type: application/json" \
  -d '{"fund_code":"005827","side":"buy","amount":50,
       "reason":"估值分位低，按定投节奏加仓","purpose":"dingtou"}'
```

注意：场外基金是**未知价交易**，下单只建 `pending` 订单，
实际份额要等 T+1 净值公布后由调度器调用 `confirm_order` 计算。

## 桌面窗口（Electron）

本系统用 **Electron** 做桌面壳：双击即开一个**没有地址栏/标签页的原生窗口**，
里面跑的就是上方那套仪表盘。

架构：Electron 主进程（`electron/main.js`）先拉起 Python 后端（uvicorn），
轮询 `/api/status` 直到 200，再创建窗口加载该地址；关窗即杀掉后端子进程。
前端为 React/Vite，构建产物在 `frontend/dist/`；FastAPI 在 `/` 提供 `dist/index.html`（改前端后需 `vite build`，点「重启应用」加载新产物，后端无需重启）。

### 首次准备

```bash
# 安装 Electron（已配置国内镜像，约几十 MB）
cd electron
npm install
```

### 启动方式

| 方式 | 命令 / 入口 | 说明 |
|---|---|---|
| 桌面快捷方式 | 双击桌面 `fund-sandbox.bat` | 直接开窗口，最省事 |
| 菜单 | 项目根目录 `run.bat` → 选 `[9]` | 同样开窗口 |
| 命令行 | `cd electron && npm start` | 带 DevTools（按 F12） |
| 仅后端 | `run.bat` → `[10]` | 只起 FastAPI，浏览器开 `127.0.0.1:8765` |

### 打包成单文件 exe（可选）

```bash
cd electron
npm install --save-dev electron-builder   # 首次额外装打包器
npm run dist                              # 输出到 electron/dist/*.exe
```

### 容错

- 若 8765 端口已被占用（上一次没关干净），Electron 会**复用**现有后端、不自起也不误杀。
- 若后端 30 秒内未就绪，窗口会显示「启动失败」提示，并自动退出，不会留下空窗口。
